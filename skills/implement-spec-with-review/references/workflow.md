# Workflow and preflight contract

The immutable source requirements are `user-requirements.txt`; accepted build amendments are `build-decisions.md`. Do not weaken their quality gates for speed.

1. Obtain repository/workdir and original high-level design plus OpenSpec proposal/design/tasks/spec/scenarios. Read applicable AGENTS.md, dirty and untracked files, build/test configuration, diagrams and supporting documents. Record hashes and exact source paths in manifest. Parse Markdown task checkboxes with original IDs; where formatting is ambiguous ask rather than invent IDs. The runner accepts an explicit reviewed manifest, not an unreliable universal OpenSpec parser.
2. Create a mapping for each original task: requirement IDs, acceptance IDs, observable scenarios/tests, dependency IDs, original order, high-risk flag and named safe-argv gates. Expose oversized tasks, missing criteria, contradictory sources and changes to order/splitting for user confirmation. Do not rewrite source task checkboxes implicitly; state/manifest supply exact completion mapping.
3. Verify actual management subagent availability and two-manager lifecycle, CLI paths/versions/help, login, stdin/noninteractive support, explicit resume, output schema/events, sandbox permissions, required process inspection (`probe.py` runtime section), original document access and attachments. Validate the intended runner host-tool environment and pass that permission requirement to each management agent; use ordinary tool approval within existing authorization as specified in CLI capabilities. Display provider/model/effort/CLI/availability for all three roles. Model labels do not determine model IDs. Previous config is only a suggestion until the user explicitly reuses it.
4. Collect approved build/lint/typecheck/test/integration/e2e argv and measure baseline. No baseline failures are implicitly exempt; exceptions name task/gate and exact evidence fingerprint, with user authorization. If no separate lint/typecheck applies to a tiny fixture, disclose this; do not represent an absent tool as a passing check.
5. Ask all unresolved questions together. Record decisions and scope. Confirm role matrix, task scope/order, acceptance gates, risk, TDD exceptions, context/session policy, finite timeout/retries/calls/active time, baseline handling and log root before code changes. Defaults in make_fixture.py apply only to the already approved smoke fixture, never automatically to a real project.
6. Create a run with runner init, run baseline gates, then runner approve with the actual user's confirmation text. A supplied configuration is not confirmation. Managers are created in App and their actual identifiers registered with bind. Never fabricate manager IDs to get past a gate.
7. Execution manager invokes initial implementer, records full gates, then Review manager invokes fresh independent reviewer and reconciliation. Same managers and explicit CLI session resume continue fixes. Orchestrator reads compact status first and consults detailed evidence only when needed.
8. Finish current task before the next. If blocked, dependents cannot run. Independently runnable tasks may proceed only when the initial plan expressly permits it and independence is established. Next task uses new managers and sessions plus previous accepted dependency contracts.
9. After all tasks pass, execute `_final` full gates and fresh selected reviewer. Final integration review has its own five-round budget, fallback after round 2, and no artificial repair-task budget reset. All gates must pass before overall completion.

## Context decision before every call

Keep App, management-agent and external CLI context separate. Record source, reliable used/capacity if exposed (otherwise null), next-read byte count and action in context assessment. Byte counts describe planned inputs, not an asserted token occupancy. Never use lifetime billed tokens as current context. Consider space for tools/output and record the rationale in assessment. A configured `ask` policy pauses on unknown capacity. A user-confirmed `checkpoint-resume` policy permits continuation with unknown usage, while preserving checkpoints, limiting read sets to relevant originals, and using fresh sessions on insufficient capacity, observed compaction needing rebuilding, invalid session or unrecoverable resume. Unknown does not prove sufficient capacity. If the planned read set cannot be assessed within the approved strategy, ask.

Fresh sessions reread constraints, decisions, acceptance, unresolved findings and relevant originals. A manager replacement must provide a reason and checkpoint, not reset rounds/retries/time. Fresh independent reviewer packets omit prior ledger/status. Unresolved old issues are provided only after independent findings have been saved.

## Inputs and ownership

Canonical logs are only written by runner. CLI test capture writes invocation-local spool files; runner verifies/imports them. The runner does not require hidden reasoning: only observable messages, decisions, outputs and evidence. No secrets in prompts/logs. Known credential patterns are redacted; users must not provide secrets as source specs. Run directories are private local artifacts, not committed. `.git/info/exclude` is updated locally, including for shared worktree common Git directories; team `.gitignore` is untouched.

A plan to create an isolated project worktree requires user confirmation; use the App worktree tool and a fixed original-root run location. Current runner expects the repo used at init to remain available. It never deletes a user's worktree.
